# Design

## Context

Сейчас класс `Game` (`duel/game.py`, ~600 строк) одновременно: окно и цикл кадров (`clock.tick` → плавающий `dt`), меню и настройки, ввод (зажатые физические клавиши `held`, геймпады → «виртуальные» клавиши), звук (вызовы `audio.shoot/melee` прямо из правил), всплывающие надписи (переведённый текст пишется в `popups` прямо из правил, «нет патронов» ограничено по `pygame.time.get_ticks()`), и все правила (выстрел, удар, артефакты, волны мобов, попадания). Отрисовка (`screens.py`, миксин) читает поля `Game` напрямую. Сущности (`entities.py`) берут случайность из общего `random`; маг двигается по набору зажатых клавиш (`Player.update(dt, keys)`). Тесты (~145) обращаются к правилам через `game.*` более 300 раз; поле всегда шагается фиксированным `DT = 1/60`.

## Goals / Non-Goals

**Goals:**
- Матч: правила и состояние партии, которые работают без окна, звука и событий pygame; шаг `step(dt, команды) → события`.
- Приложение превращает ввод в команды, а события — в звук и надписи; хотсит работает как раньше.
- Повторяемость партии: одно зерно + одни и те же команды → одно и то же состояние.
- Номера объектов для будущих снимков.
- Доказать, что поведение не изменилось (отпечаток партии).

**Non-Goals:**
- Снимки состояния и отрисовка по снимку (этап 1). Методы `draw` у сущностей пока остаются в `entities.py`.
- Сеть, сервер, лобби (этап 2+).
- Изменение правил, баланса, управления или экранов.

## Decisions

1. **Матч — отдельный модуль `duel/match.py`, класс `Match`.** В него переезжают состояние партии (маги, пули, мобы, снаряды, артефакты, пачки, стены, двойники, волны, время партии, победитель) и правила (`fire`, `melee`, `use_item`, `apply_item`, `give`, волны, попадания, выпадение…). `Game` остаётся приложением и владеет `self.match`; `restart()` создаёт новый матч. Альтернатива — наследование `Game(Match)` — снова склеило бы правила с окном.

2. **Команды — `duel/commands.py`, `Command(move=(dx, dy), fire, melee, use_slot)`.** Движение — состояние на такт, остальное — «нажатия» с прошлого такта. Приложение собирает команду каждого мага из клавиатуры и геймпада. `Player.update` получает `(dx, dy)`, а не клавиши; клавиши игрока остаются у приложения. Альтернатива — передавать набор клавиш в матч — сохранила бы зависимость правил от раскладки и pygame.

3. **Порядок внутри шага сохраняет нынешний.** Сейчас нажатия (выстрел, удар, ячейка) обрабатываются до `update`, где маги двигаются. В `step` сначала применяются нажатия из команд, затем движение и остальное — иначе отпечаток разойдётся.

4. **События — простые записи с ключами, без текста и цвета.** Например `("shot", "blue")`, `("pickup", "red", "shield")`, `("used", target, kind)`, `("ammo", player, 20)`, `("no_ammo", player)`, `("mob_dead", x, y)`, `("wave", n, count, hp)`. Приложение переводит их в звук, надпись на языке игрока и цвет. Так сервер не зависит от языка клиента. Ограничение «нет патронов» раз в секунду считается по времени матча.

5. **Фиксированный такт 60 Гц в приложении.** Приложение копит время кадра и делает целое число шагов матча по `1/60` (не больше нескольких за кадр, чтобы не «догонять» бесконечно после паузы). Тесты уже шагают по `1/60`, поэтому для них ничего не меняется.

6. **Случайность — `match.rng = random.Random(seed)`.** Всё, что сейчас берёт `random.*` в правилах и сущностях (места мобов и пачек, выбор артефакта, двойники, волна пуль), получает генератор матча (сущности — через матч или параметром). Это делается **последним шагом**, после проверки отпечатка: смена источника случайности неизбежно меняет последовательность чисел.

7. **Номера объектов — счётчик матча.** Каждый новый объект получает `id` из `match.next_id()`; маги — постоянные `"blue"` / `"red"`.

8. **Отпечаток партии.** До начала перестройки записываем эталон: детерминированный прогон (два бота со своим генератором, который не трогает общий `random`; фиксированное зерно; несколько минут игрового времени) и хеш состояния каждые N тактов. После переноса правил (до шага 6) прогон через новый API с теми же действиями ботов должен дать тот же хеш. После шага 6 эталон пере-записывается, а вместо него проверяется повторяемость: два прогона с одним зерном совпадают, с разными — различаются.

9. **Тесты правил переходят на матч.** Фикстура `match` даёт матч без окна; правила проверяются как `match.apply_item(...)`, `match.mobs`, `step(match, …)`. Тесты меню, ввода, геймпада, языков, отрисовки остаются на приложении (`game`). Перевод механический: замена обращений к перенесённым полям и методам.

## Risks / Trade-offs

- [Большой механический перенос — легко потерять мелочь (порядок обработки, крайний случай)] → отпечаток партии до/после ловит любое изменение поведения; плюс все существующие тесты.
- [Конфликты с параллельными игровыми изменениями] → на время этапа 0 новые механики не начинаем; этап короткий и сразу вливается в `main`.
- [Матч всё ещё импортирует pygame через сущности (методы `draw`)] → импорт pygame без окна безопасен; отрисовка уезжает из сущностей на этапе 1. Отдельный тест: матч работает без созданного окна.
- [Переход на свой генератор меняет случайные последовательности] → делается последним, после проверки отпечатка; повторяемость проверяется отдельно.

## Migration Plan

Всё — в `main`, несколькими коммитами по группам задач; после каждого — зелёные тесты. Откат — `git revert` соответствующих коммитов: поведение для игрока не меняется, данные и настройки не затрагиваются.
