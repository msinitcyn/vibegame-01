# Design

## Context

После этапа 0 правила живут в `Match` (`duel/match.py`), приложение (`Game`) превращает ввод в команды и события в звук и надписи. Но экран (`screens.py`) по-прежнему читает объекты матча напрямую: `self.match.bullets`, `self.match.walls`, `p.effects`, `self.match.clones_of(p)`, `self.match.winner`. Сущности (`entities.py`) рисуют себя сами (`Player.draw`, `Unit.draw_effects`, `Mob.draw` и т. д.) и поэтому импортируют `pygame`, спрайты и значки. Всплывающие надписи берут положение мага из матча (`m.player(id).x`). Клиенту в сети объекты матча недоступны — у него будет только присланный снимок.

## Goals / Non-Goals

**Goals:**
- Снимок матча из простых значений, который проходит через JSON без изменений и содержит всё, что нужно экрану.
- Экран поля, статус и надпись о победе рисуются только по снимку.
- Отрисовка уходит из сущностей; правила (`match.py`, `entities.py`) не рисуют.
- Хотсит работает через снимки; картинка для игрока не меняется.

**Non-Goals:**
- Сеть, сервер, протокол, сжатие снимков, интерполяция между снимками (этап 2).
- Флаги `--connect`, `--windowed`, геймпад в фоновом окне (этап 2).
- Изменения правил, баланса, экранов, звуков.

## Decisions

1. **Снимок — `duel/snapshot.py`, функция `snapshot(match) -> dict`.** Только `int`, `float`, `str`, `bool`, `None`, `list`, `dict` с ключами-строками. Альтернатива — dataclass'ы снимка: удобнее в коде, но их пришлось бы отдельно превращать в JSON и обратно; словарь сразу годится для отправки.

2. **Состав снимка** (ключи короткие, но читаемые):
   - `time`, `wave`, `next_wave`, `winner` (`"blue"` / `"red"` / `None`);
   - `players`: `id`, `x`, `y`, `r` (радиус с учётом эффектов), `hp`, `ammo`, `effects` (имя → остаток секунд), `shield_hits`, `items` (4 ячейки), `queue`, `hit_flash`, `melee_flash`;
   - `bullets`: `id`, `x`, `y`, `owner`;
   - `mobs`: `id`, `x`, `y`, `r`, `hp`, `max_hp`, `ranged`, `facing`, `flash`, `target` (`id` мага или `None`);
   - `mob_shots`: `id`, `x`, `y`;
   - `artifacts`: `id`, `kind`, `x`, `y`;
   - `ammo_packs`: `id`, `x`, `y`, `life`;
   - `walls`: `id`, `owner`, `x`, `y1`, `y2`, `life`;
   - `clones`: `id`, `owner`, `x`, `y`, `r`, `life`, `effects`.
   Цвет, спрайт и направление клиент выводит из `blue` / `red` (таблица в модуле отрисовки), поэтому в снимок не попадают.

3. **Округление при снятии.** Координаты — до 0,1 пикселя, таймеры — до 0,01 секунды. Округлённые числа проходят через JSON без изменений, поэтому «снимок → JSON → снимок» даёт тот же словарь, а снимок короче для сети. Отрисовка всё равно приводит координаты к целым пикселям.

4. **Отрисовка — `duel/render.py`.** Функции по видам объектов: `draw_player`, `draw_clone`, `draw_effects`, `draw_bullet`, `draw_mob`, `draw_mob_shot`, `draw_artifact`, `draw_ammo_pack`, `draw_wall`, и `draw_field(surf, snap, font)` — всё поле в нынешнем порядке слоёв (стены, артефакты, пачки, двойники, мобы, снаряды, пули, маги). Код переносится из методов `draw` сущностей почти без изменений: `self.x` → `o["x"]`, `self.owner.color` → `COLOR[o["owner"]]`, `self.frozen` → `"freeze" in o["effects"]`. Из `entities.py` убираются `draw`, `draw_effects` и импорты отрисовки. Альтернатива — оставить `draw` у сущностей и «оживлять» сущности из снимка: лишняя связь клиента с правилами.

5. **Приложение хранит последний снимок `self.snap`.** Обновляется при `restart()` и после каждого такта `update()`. `screens.py` читает только `self.snap` (`draw`, `draw_hud`, `draw_wave_timer`, `status_chips(p, snap)` — стены и двойники игрока считаются по снимку). Меню, справка и настройки снимок не используют.

6. **Надписи по снимку.** `handle_events(events)` вызывается после снятия снимка и берёт положение мага из `self.snap`. Положение — после такта, а не в момент события (разница — путь мага за 1/60 секунды, глазом не видна). Так клиент в сети сможет показывать надписи из присланных событий и снимка.

7. **Проверки.**
   - снимок → `json.dumps` → `json.loads` равен исходному снимку (несколько моментов случайной партии, со всеми видами объектов и эффектов);
   - картинка поля по снимку и по снимку после JSON совпадает пиксель в пиксель;
   - экран рисуется, когда у приложения нет доступа к матчу (`game.match` подменён заглушкой, которая падает при обращении) — значит, экран читает только снимок;
   - `entities.py` и `match.py` не импортируют `pygame`, `render`, `sprites`, `icons`;
   - отпечаток партии совпадает с эталоном (правила не трогаем);
   - визуальная проверка: картинка поля с эффектами до и после переноса (рендер в файл).

## Risks / Trade-offs

- [Потерять мелочь при переносе отрисовки — мигание стены, кольцо щита, вспышка удара] → перенос почти построчный; рендер одной и той же сцены до и после сравнивается глазами; тесты рисуют все эффекты.
- [Снимок без нужного поля — экран упадёт или нарисует не то] → тест «экран без доступа к матчу» ловит любое обращение мимо снимка.
- [Снимок каждый такт — лишняя работа в хотсите] → объектов на поле десятки, словарь на 60 тактов в секунду незаметен; при необходимости снимать один раз на кадр.
- [Надпись чуть смещается — положение после такта] → разница меньше пикселя-двух, отпечаток не затрагивает.

## Migration Plan

В `main` (`master`), коммитами по группам задач, после каждой — зелёные тесты и совпадение отпечатка. Откат — `git revert`; данные и настройки не затрагиваются.
