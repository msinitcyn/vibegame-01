# Сетевая версия — дорожная карта

Цель: играть на разных компьютерах, сохранив хотсит (два игрока за одним компьютером). Идём маленькими шагами; после каждого этапа игра работает. Каждый этап — отдельное изменение OpenSpec (`openspec/changes/`).

## Архитектура

**Авторитетный сервер.** Правила игры считаются в одном месте — в «матче» на сервере. Клиенты отправляют команды своего игрока (движение, выстрел, удар, ячейка) и получают снимки состояния поля, а сами только рисуют, играют звук и читают ввод. Рассинхронизации и подделки нет: на клиенте нет своей копии правил.

Хотсит — тот же матч и тот же клиент в одном процессе, оба игрока за одной клавиатурой.

```
клиент: ввод → команды ──►  сервер: матч.step(команды), фиксированный такт
клиент: экран/звук    ◄──  снимок состояния + события (звуки, надписи)
```

Решения, принятые на обсуждении:

- Сначала сервер запускает один из игроков («Создать игру»), второй подключается по адресу. Потом — возможна централизация.
- В перспективе серверов много и есть **портал**: список серверов, игроки, мини-турниры; матчмейкинг — необязательно (играют друзья).
- **Зрители** — позже, но протокол сразу знает роль подключения (игрок / зритель).
- Формат данных — JSON, транспорт — TCP; бинарный формат и UDP — только если понадобится.

## Этап 2 — выполнен (2026-11-19)

- `lan-server-client`: сервер без окна (`python -m duel.server`, `--bot`), клиент `main.py --connect АДРЕС --windowed --pad N`, геймпад без фокуса окна, приветствие с версией протокола и ролью.
- `lan-menu-smooth`: «Создать игру по сети» и «Подключиться» в меню, экран ожидания с адресом, бот на месте второго, Esc и обрыв — в меню; сервер ждёт оба места; снимки 30/с и плавная анимация с задержкой 0,1 с; протокол 2.

Отличия от исходного плана: сообщения — JSON по строкам (а не с длиной) — проще и читается глазами; снимки сразу 30/с.

## Этап 3 — что уже есть (2026-11-19)

- `lan-discovery`: поиск игр в локальной сети — экран «Подключиться» спрашивает сеть по UDP 5556, серверы отвечают; список с состоянием, выбор стрелками; ручной ввод остаётся.
- `player-names`: имя игрока в настройках — в панели, на экране победы и в списке игр; бот подписан; первая найденная игра выбирается сама. Протокол остался версии 2 (имена — необязательные поля).
- `lobby-reconnect`: лобби с «готов», реванш по готовности обоих, соперник вышел → лобби; обрыв (закрытие или 3 с тишины) → пауза, место держится 30 с, клиент сам возвращается по ключу; «создатель вышел» (`bye`). Протокол 3.

## Этап 4 — автообновление (выполнен 2026-11-20, `auto-update`)

- **Где проверять**: `https://api.github.com/repos/<владелец>/<репо>/releases/latest` — тег (`v0.5.0`) и список файлов выпуска. Без ключей; лимит 60 запросов в час с адреса — проверяем один раз при запуске, в фоне, без задержки меню. Нет сети — молча работаем дальше.
- **Сравнение**: версия из тега против своей (`pyproject.toml` → вшита в сборку). Новее — в меню строка «Доступна версия X» и пункт «Обновить».
- **Linux**: скачать `spellgunners-linux.tar.gz`, проверить SHA-256 (файл `SHA256SUMS` в выпуске), заменить `~/.local/bin/spellgunners` (у пользователя есть права — его ставит `install.sh`), перезапуститься (`os.execv`).
- **Windows**: работающий `.exe` заменить нельзя — скачать `spellgunners-setup.exe`, проверить сумму, запустить его тихо (`/SILENT /CLOSEAPPLICATIONS`) и выйти; установщик ставит в профиль пользователя без прав администратора (`PrivilegesRequired=lowest`) и запускает игру снова.
- **Сборка**: CI добавляет в выпуск `SHA256SUMS`.
- **Сеть**: при «разные версии протокола» экран подключения предлагает «Обновить».
- **Запуск из исходников** (`python main.py`): не обновляемся, только пишем, что есть новая версия (обновление — `git pull`).
- Настройка «Проверять обновления» (по умолчанию — да).

## Этап 5 — зрители (выполнен 2026-11-20, `spectators`)

- Протокол 4: в `join` роль `player` / `spectator`; зрителю — `watch`, он получает снимки и события, ничего не шлёт; до 8 зрителей; число — в каждом снимке.
- Из меню: мест нет → клиент сам подключается зрителем. Переподключение — тоже зрителем.

## Заранее в протоколе (чтобы потом не переделывать)

- версия протокола в первом сообщении;
- роль подключения: `player` / `spectator`;
- имя и идентификатор сервера и игрока;
- отдельное сообщение с результатом партии (для портала и турниров).

## Как вести параллельно с игровыми изменениями

- Этапы 0 и 1 — сразу в `main`: они затрагивают почти весь код, и чем быстрее они там, тем меньше конфликтов. На время этапа 0 новые механики лучше не начинать.
- После этапа 0 новые артефакты и механики пишутся в новой структуре: правила — в матче, вид — в клиенте.
- Этапы 2+ — в ветке `feature/network`, в отдельном рабочем каталоге (`git worktree`, например `~/projects/fast-game-network`), чтобы параллельно работать над игрой в `main`. `main` регулярно вливается в ветку; ветка вливается в `main`, когда «Создать игру / Подключиться» работают.
